# Supabase標準メールでのマジックリンク実接続手順

## 今回の実装と検証範囲

マジックリンク送信、PKCEによる認証コード交換、サーバーでの本人確認、ログアウト、再読み込み時の認証確認を実装した。既存OTP処理も維持し、将来SMTPを準備したら設定で切り替えられる。

こちらでは実際のProject URL・publishable key・利用者メールを受け取っていないため、実プロジェクトへの送信/メール到達/リンク認証は未実施。自動テストとブラウザはモック応答で検証する。以下の手順を利用者のテスト環境で行い、実接続を確認する。設定値は初期状態で空欄、接続無効。

## 1. 手元の作業ファイルを準備する

最新版のローカル認証テストには `test/supabase-local-auth` ブランチを使用する。mainをpullするだけでは取得できない。Windowsでの取得・起動手順は [windows-local-test.md](windows-local-test.md) を参照する。古い認証画面を使わないよう `js/public-config.mjs` にmethod/redirectUrl、`js/auth-callback.mjs` にPKCE処理があることを確認する。

現在のデータがある場合は、設定画面から一括JSONをダウンロードして保管する。Gitでのローカル状態保全も済ませる。

## 2. ローカルサーバーとRedirect URLを合わせる

```sh
cd hazure-no-kioku
python scripts/serve_local.py --port 8000
```

Pythonのコマンドがpython3の場合は読み替える。新しいサーバーはログインコードを含むリクエストURLをログに記録しない。既に8000番を使用している場合は自分の既存サーバーを終了するか、別ポートを選びSupabaseの許可URLも合わせる。

ブラウザで `http://127.0.0.1:8000/` を開く。Supabaseに登録したローカルRedirect URLが別のポート/localhost表記/index.html付きの場合は、実際に開くURLと完全に一致させる。同じホスト・ポートで認証と既存データを扱う。localhostと127.0.0.1は別の保存領域である。

## 3. 自分のPCで公開設定を入力する

`js/public-config.mjs`のauth部分だけを以下の形で設定する。URLとキーは自分のプロジェクトからコピーする。下の文字列は説明用であり、そのまま有効な設定ではない。

```js
auth: Object.freeze({
  enabled: true,
  projectUrl: '自分のSupabase Project URL',
  publishableKey: '自分のsb_publishable_形式の公開キー',
  method: 'magic-link',
  redirectUrl: 'http://127.0.0.1:8000/'
})
```

redirectUrlは上で確認した実際のURLに置き換える。空欄の場合は、開いているアプリのorigin＋pathnameを戻り先とする。戻り先にquery/hashや別originを指定しない。PUBLIC_CONFIGの他の項目は維持する。認証有効時はローカルでもPLUSデモによる解放を無効にする。

公開用キーは秘密鍵ではなく、ブラウザへ配信する前提の値。ただし今回の指定どおり、作業用の値はGitへ入れない。service_role、sb_secret_キー、DBパスワード、Stripe秘密鍵は使用しない。

## 4. Supabase側の確認

- Email認証が有効になっている。
- 「初めて利用する」を使う場合は新規登録が許可されている。
- AuthenticationのURL Configurationで、実際のローカル戻り先がRedirect URLsに登録されている。
- Site URLも必要に応じて実際のテスト先を確認する。誤った外部URLを指定しない。
- 標準メールのテンプレートはそのままでよい。今回 `{{ .Token }}` への編集は不要。
- 標準送信には宛先/送信回数の制限がある。初期テストはプロジェクトのチームで許可されたメールなど、送信できるアドレスで行う。任意の一般利用者へ送れると仮定しない。
- SMTPやStripe、契約権限DB/RLSの作成は今回不要。

## 5. 実際の送信・ログイン

1. アプリを再読み込みし「設定・データ → アカウント・ログイン」を開く。
2. 「ログインリンクを送信・再送」が有効なことを確認する。
3. 自分の受信できるメールを入力する。未登録の場合だけ「初めて利用する」にチェックする。
4. 送信する。メールが届かなければ迷惑メール、標準送信の宛先制限、Rate Limits、Authログを確認する。何度も連打しない。
5. **送信したのと同じブラウザで、メール内の最新リンクを開く。** 同じブラウザ内の別タブでもよい。スマートフォンのメールアプリ内ブラウザと通常ブラウザ、別PC、プライベートモードの混在は避ける。
6. アプリの認証画面に戻り、「認証中 → ログイン済み」と自分のメールが表示されることを確認する。アドレスバーからcode/認証エラーが除去される。
7. 「PLUS契約権限：未確認」のままで、ログインだけでPLUS機能が開かないことを確認する。

PKCEの確認情報は独立localStorageキー `hazure-no-kioku-pkce-v1` に最大1時間だけ保管する。最新の送信情報を使い、コード交換後に除去する。ユーザーデータJSONに含めない。同じoriginの新しいタブでリンクを開けるようlocalStorageを使用する。確認情報がない/別プロジェクト/古い場合はログインを拒否し、再送を案内する。

Supabaseがcode付きPKCEではなくaccess_token付きfragmentを返した場合は、その方式を自動受入れせず、新しいPKCEリンクでやり直す。URL内のトークンは読み取り後に除去する。リンク全体、認証コード、トークン、個人メールのスクリーンショットやログは共有しない。

## 6. 再読み込み・ログアウト・FREE確認

- ログインしたタブを再読み込みする。保存セッションをサーバーで確認し、ログイン済みに戻ることを確認する。
- ログアウトを押し、未ログインに戻ることを確認する。再読み込み後も未ログインであることを確認する。
- 記録・お気に入り・回避額・プランは削除されていないことを確認する。記録は端末内のままで、自動同期しない。
- 認証セッションはsessionStorageなので、ログインタブを閉じると原則として再ログインが必要。他のタブへ自動共有しない。これは現段階の仕様。
- 接続を一時的に切り、送信失敗の案内が出てもホームの衝動ボタン、5秒演出、記録等のFREE機能が動くことを確認する。
- 一括JSONにアクセストークン・refresh token・PKCE情報が入っていないことを確認する。

## 7. よくある失敗

| 状況 | 確認すること |
|---|---|
| ボタンが無効 | enabled/Project URL/公開キー。設定変更後の再読み込み |
| メールが来ない | 標準送信の宛先制限、迷惑メール、登録許可、送信上限 |
| 違うURLへ戻る | Redirect URLsと実際のアプリURLの完全一致 |
| 確認情報がない | 同じブラウザ・同じoriginか。最新リンクを再送 |
| 期限切れ/使用済み | 新しいリンクを送り、最新メールのリンクだけ開く |
| 通信失敗 | 接続状態とProject URL。FREEはそのまま利用可能 |
| ログイン後PLUSが使えない | 正常。契約権限DB/決済はまだ実装していない |

## 8. 設定値をGitHubへ入れない確認

テスト後、URL・キーを空欄、enabled:falseに戻す。必要なら値はリポジトリ外の安全な場所で管理する。設定ファイルを消したり、Gitのskip-worktreeで変更を隠したりしない。

```sh
node scripts/check-public-config.mjs --working-tree
```

このコマンドは値を表示せず、空欄・接続無効かを確認する。値が残れば失敗する。commitが別途承認された後にステージした場合は、さらに以下を実行する。

```sh
node scripts/check-public-config.mjs
```

こちらは**ステージ済みの内容**を確認する。作業ファイルだけを空欄に戻しても、以前の設定がステージに残っている場合を検出する。git diff --cachedで意図したファイルだけか確認するが、その出力に設定値がある場合はチャットへ貼らない。

このチェックは自動のGitフックではないため、将来commitする直前に手動実行する。Supabase公開キーを実際の本番へ埋め込む場合は別途明示承認・確認を行い、チェック方針を変更する。秘密鍵が漏れた場合は空欄に戻すだけでは済まず、キーの失効・再発行が必要。

## 9. 将来のOTPへの切り替え

Custom SMTPとコード形式のメールテンプレートを準備し、桁数等を確認した後、methodを `otp` に変更する。6桁入力画面が表示され、既存のsendOtp/verifyOtp処理を使う。認証画面と輸送処理を分離しており、FREEや契約権限の設計を変更せず切り替えられる。

実サービスとの互換性・メール到達・ログイン成功は利用者テストで確認するまで未検証として扱う。結果を共有する場合は成功/失敗の段階とエラー案内だけを伝え、キー・コード・メールリンクは送らない。
